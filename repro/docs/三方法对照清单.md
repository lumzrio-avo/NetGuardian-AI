**Granger 是成对检验、可跳过、可并行，是三者中唯一能处理全量指标的。**

### PCMCI 的变量集来源：**"删常量列"的副作用**（已核实）

经与 PCMCI 运行方确认，并结合本地结果实测复核，PCMCI 的变量集**不是有意挑选**的，
而是常规预处理步骤「删除 `std == 0` 的常量列」的**副作用**：

```
原始 data.csv
  ↓ 删 time / latency-50
  ↓ 删 std == 0 的常量列
  ↓ 剩下 ~50 个指标     ← 全部是 container-memory-*
```

| 指标类型 | 是否容易 std==0 | 结果 |
|---|---|---|
| `container-memory-*` | 波动大（内存占用天生抖动） | ✅ 保留 |
| `container-cpu-*` | 部分服务恒为 0 | ❌ 被删 |
| `istio-latency-90` | 正常运行时稳定 | ❌ 被删 |
| disk / network | 多数场景无流量 | ❌ 被删 |

> **不是"选了 memory"，而是"只有 memory 活下来了"。**

**本地实测复核**（`结果/pcmci/pcmci结果/`）：

| 目录 | 节点数 | 实际构成 |
|---|---|---|
| `output_ss` | **50**（125 例恒定） | **100% 为 `*_container-memory-*`**：usage-bytes 12 / working-set 12 / rss 12 / max-usage 9 / cache 4 / mapped-file 1 |
| `output_tt` | **50**（125 例恒定） | **100% 为 `*_container-memory-*`**：usage-bytes 14 / rss 13 / working-set 13 / max-usage 10 |
| `output_ob` | 34~47 | **正常**：`adservice_cpu`、`cartservice_cpu` … 短名齐全 |

**与 `summary_v2`（variant = `new_add_latency`）的算术闭环**：

| 数据集 | 纯 memory 版 | `istio-latency-90` 列数 | 相加 | `summary_v2` 实测 |
|---|---|---|---|---|
| RE1-SS | 50 | **8** | 58 | **58.00（恒定）** ✅ |
| RE1-TT | 50 | **29** | 79 | **71~79，均值 75.54** ✅ |

⇒ 证实运行方说明：**最初版只剩 memory；上周重跑时把 `istio-latency-90` 手动加回**（即 `new_add_latency`）。
**但即便加回 latency，图里仍然没有 cpu / disk / network。**

**为什么 OB 不受影响**：OB 的指标本身就是 `{service}_cpu / _mem / _latency / _load`，正常运行也在波动，
不会被 `std==0` 误删。SS / TT 是 Prometheus 长名指标，大量指标在正常时平坦 → 被整体剔除。

### ⚠️ 已确认窗口，但出现**硬矛盾**（待定位）

运行方确认：`std` 是在 **1200 点全窗口（600 正常 + 600 异常）** 上算的。

但这与 Granger 的实际结果**直接冲突**：

| | 判据 | 同一份 RE1-SS、同一 1200 点窗口的结果 |
|---|---|---|
| **Granger** | `drop_constant`：`(df != df.iloc[0]).any()`<br>（**数学上等价于 std == 0**） | 275 节点，含 **cpu 类 48 个**、latency 类 32 个 |
| **PCMCI** | `std == 0` | 50 节点（**125 例恰好都是 50**），去重后 **cpu 0 个、latency 0 个** |

**等价判据 + 同一份数据 + 同一窗口 → 不可能得出相反结果。**
⇒ 至少有一个前提不成立，需向运行方核对：

1. 算 `std` 时那个 `data` 变量**到底是什么**？（是否已做过差分 / 取 rate / 归一化 / 只取了一段）
2. 为什么 **125 个案例的节点数恰好都是 50**？代码里是否有 `[:50]` 之类的截断？
3. 读取的 `data.csv` 路径与 Granger 是否同一份？

**顺带记录**：125 个案例的节点**列表内容各不相同**（125 种签名），但**数量恒为 50**。
数量完全恒定这一点本身就不像自然筛选的结果。

### PC 的「窗口 / alpha / 变量预筛」三系统不一致（2026-09-25 核实）

用 375 个案例日志（`run_log_pc.txt`）逐例提取实际配置，结果如下（每项均为 125/125 恒定）：

| 项 | RE1-OB | RE1-SS | RE1-TT |
|---|---|---|---|
| 原始数据行数 | 1200 | 721 | 961 |
| `t_fail`（故障索引） | 600 | 600 | 600 |
| **参与建图的窗口** | **正常窗口 480 行** | **全窗口 721 行**（normal + anomaly） | **正常窗口 480 行** |
| **PC 样本数** | 480 | **721** | 480 |
| **alpha** | 0.05 | **0.1** | 0.05 |
| 变量筛选 | 仅删常量列（44~47） | **相关性预筛 `max_features=40, corr_threshold=0.95`** → 恒 40 | 仅删常量列（9~31） |

日志原文对照：

```
[OB]  正常窗口数据形状: (480, 46) (前 480 行)
      运行 PC 算法: alpha=0.05, indep_test=fisherz, 样本数=480, 变量数=44

[SS]  特征预筛选: max_features=40, corr_threshold=0.95
      预筛选后: 40 个变量 (从 230 降维, 保留率 17.4%)
      使用全窗口数据: shape=(721, 40) (normal+anomaly)
      运行 PC 算法 (Enhanced): alpha=0.1, indep_test=fisherz, 样本数=721, 变量数=40

[TT]  正常窗口数据形状: (480, 50) (前 480 行)
      运行 PC 算法: alpha=0.05, indep_test=fisherz, 样本数=480, 变量数=49
```

**核实结论**：

1. **「全窗口」只出现在 SS** —— `grep "使用全窗口数据"`：OB `0/125`、SS `125/125`、TT `0/125`。
2. **OB / TT 未被波及** —— 二者日志时间为 08-19~08-20，SS 为 08-24，改动发生在 SS 之后，
   且 OB/TT 日志中确实是旧配置。
3. **但 SS 目前在三处与 OB/TT 不一致**：窗口（全窗口 vs 正常窗口）、`alpha`（0.1 vs 0.05）、
   变量筛选（相关性预筛 vs 仅删常量列）。

⇒ 这是一条**新增的、独立于"变量集规模"的不一致维度**，需要在统一口径时一并处理。

#### 三方法的窗口处理对照（2026-09-25 补充核实）

| 方法 | RE1-OB | RE1-SS | RE1-TT | 依据 |
|---|---|---|---|---|
| **Granger** | 全窗口（600 正常 + 600 异常） | 同左 | 同左 | `run_granger.py:238-241`，与官方 `main.py:213-214` 逐行一致 |
| **PCMCI** | **全窗口**（高置信推断） | 未确认 | 未确认 | 见下方"节点数吻合"证据 |
| **PC** | **正常窗口 480 行** | **全窗口 721 行** | **正常窗口 480 行** | 375 个 `run_log_pc.txt` 逐例提取 |

**PCMCI 用全窗口的证据（OB）**：把 PCMCI 的 OB 节点数与 Granger 的 OB 节点数逐例对比 ——

| | 结果 |
|---|---|
| 节点数**完全相同** | **83 / 125** |
| 不同（差值） | 42 / 125，**差值范围仅 −1 ~ +1**（均值 0.86） |

Granger 的 OB 节点数是「全窗口 1200 点上删常量列」得到的。若 PCMCI 用的是正常窗口 480 点，
大量在故障段才有波动的列会变成常量被剔除 → 节点数应系统性偏少，不可能 83/125 完全相同。
⇒ **PCMCI 的 OB 用的是全窗口**（与 Granger、与官方一致）。
（±1 的差异来自 `std()==0` 与 `(df != df.iloc[0]).any()` 的浮点边界差异。）

**SS / TT 无法从节点数判断**：PCMCI 在这两个数据集上被 `select_features(max_features=50)` 截断到恒 50，
窗口信息被覆盖。用 TT 原始数据做过反推实验（`结果/probe_pcmci_window.py`）：全窗口 40/50、
正常窗口 32/50 —— **方向偏向全窗口，但未达 100%，只能算倾向，需向运行方确认**。

#### ⚠️ 另一处发现：PC 的"结合异常分数"是死代码

`结果/pc/pc_module.py:231-245`：

```python
if anomaly_scores is not None:
    valid_anomaly = anomaly_arr[non_const_idx]
    valid_anomaly_norm = (valid_anomaly - valid_anomaly.min()) / (...)
    anomaly_dict = {valid_names[i]: valid_anomaly_norm[i] for i in range(n_valid)}
    logger.info("已结合异常分数进行辅助评分 (anomaly_scores 提供)")   # ← 只打日志
```

`anomaly_dict` 算完之后**从未被使用**；最终保存的排名（`pc_summary.csv` 的 `score` 列）
就是 `_run_pagerank()` 返回的**纯 PageRank 分数**。

⇒ **PC 的排序实际是纯 PageRank**（与官方式一致），日志里那句"已结合异常分数"是误导性的。
⇒ 这一点很重要：若统一口径时选择"正常窗口"，等于**用更少的样本建图、却并没有换来基于异常分数的排序**
  —— 需要一并决定排序阶段是否真的引入故障信息。
⇒ 修复成本低：PC 三系统合计约 15 分钟即可全部重跑（OB ≈1.9 s/例、SS ≈4.8 s/例、TT ≈0.34 s/例）。

## 4. 容错机制（异常处理）

| 项          | Granger                                                                      | PCMCI                                 | PC                                                                   |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------- | -------------------------------------------------------------------- |
| 官方实现是否裸调用  | ✅ **是**（无任何保护）                                                               | ❌ 否，**官方自带**                          | ✅ **是**（无任何保护）                                                       |
| 官方遇错时的行为   | `main.py:314-315` 为 `raise e`，  
且 `main.py:325` 的批量循环无异常保护  
→ **整个评测任务终止** | 不适用                                   | 同 Granger                                                            |
| 本项目的处理     | `try/except` 包住  
`grangercausalitytests`                                    | 无（不需要）                                | ① 预处理阶段**预剔除常量列**（`std ≤ 1e-10`）  
② 案例级 `try/except` → 返回**全零邻接矩阵** |
| 容错**粒度**   | **单个有序对 (i,j)**                                                              | 条件集内的单个变量                             | **整个案例**                                                             |
| 语义         | 算不了的边 → 记为"无因果边"，继续                                                          | 常量变量踢出条件集；`LinAlgError` → `resid = y` | 整例失败 → 空图                                                            |
| **实际触发过吗** | ✅ 触发过

## 5. 评估口径（三套实现各不相同，引用时需注明）

### 官方规则

**节点名解析**（`main.py:380,394`）

```python
s_ranks = [Node(x.split("_")[0].replace("-db", ""), "unknown") for x in ranks]
f_ranks = [Node(x.split("_")[0], x.split("_")[1] if "_" in x else "unknown") for x in ranks]
```

即：**节点名按第一个下划线切成 `(服务, 指标)`**。

**真值（metric 级）—— 官方代码里有两套并存**：

| 官方位置 | 真值 `metric` | 是否映射故障名 |
|---|---|---|
| `main.py:397`　`f_evaluator`<br>（逐 service-fault 写入 `eval_data`） | `fault` 原样：`cpu` / `mem` / `delay` / `loss` / `disk` | ❌ 不映射 |
| `main.py:413-432`　`f_evaluator_lat` / `_loss` / `_io` …<br>（**打印输出的汇总表用的就是这一套**） | `delay`→`latency`、`loss`→`latency`、<br>`disk`→`diskio`、`cpu`/`mem`/`socket` 原样 | ✅ **映射** |

`Node.__eq__` 为严格等值比较（`classes/graph.py`），`Evaluator` 用 `answer in ranks[:k]` 判定，
因此**真值 metric 必须与节点名切出的第二段完全一致**才算命中。

### 三方法的实际口径

| | 节点命名 | 评估用的真值 metric | 对应官方哪一套 |
|---|---|---|---|
| **Granger** | **官方原始列名**<br>`carts_container-cpu-usage-seconds-total` | `latency` / `diskio` / `cpu` / `mem`<br>（`FAULT_TO_METRIC` 映射） | ✅ 与官方**映射版**一致<br>（`main.py:413-432`） |
| **PC** | **官方原始列名**<br>`orders-db_container-memory-cache` | 同上（实测取值 = `cpu/diskio/latency/mem`） | ✅ 同 Granger |
| **PCMCI** | **原始列名**（同 Granger/PC）<br>`carts_container-memory-usage-bytes` | `delay` / `disk` / `cpu` / `mem`<br>（不映射） | ✅ 与官方**不映射版**一致<br>（`main.py:397`） |

**⇒ 三种实现各自遵循了官方的一套口径，但官方自身即两套并存**，
因此三方的指标级真值命名形式不统一 —— 这不是任一方自行引入的偏离。

### 后果

| 数据集 | 指标级（Mtr-AC@k）能否算 |
|---|---|
| RE1-OB | ✅ 基本可用（节点名本来就形如 `adservice_cpu`） |
| **RE1-SS / RE1-TT** | ⚠️ 大面积无法匹配（受官方命名规则所限） |

**原因**：SS/TT 的原始列名是 Prometheus 长名，官方规则切出来是

## 附：一句话总结现状

**服务级指标可横向比较（需注明各方法输入规模不同）；指标级在 OB 可用，在 SS/TT 受官方命名规则所限无法匹配。
  
变量集差异源于算法在高维下的物理限制，不是实现错误 —— 但 PCMCI 的抽样规则需要补一份记录。**

### 附：统一口径的目标形态（仅记录，改进阶段执行）

**关键区分**：SS/TT 上「指标级恒为 0」有两种性质，不能用同一种办法解决。

Granger 的 `rank_of_truth_metric == "not_found"` 统计：

| 数据集 | cpu | mem | delay | loss | disk |
|---|---|---|---|---|---|
| RE1-OB | 0/25 | 0/25 | 0/25 | 0/25 | **25/25** |
| RE1-SS | **25/25** | **25/25** | **25/25** | **25/25** | **25/25** |
| RE1-TT | **25/25** | **25/25** | **25/25** | **25/25** | **25/25** |

- **OB 的 0** ＝ 「节点存在、但排名靠后」：名次 19~36（节点数 46），进不了 top-5。
  统一真值口径**不会**改变这类结果。
- **SS / TT 的 0** ＝ 「节点**不存在**」：真值 metric 名与节点名切出的第二段永远不相等。

**⇒ 统一真值命名只能解决"用哪套映射"的问题，无法解决 SS/TT 的节点缺失。**
要解决后者，必须让节点命名变成 `{service}_{指标族}` 形式。

**但直接改名会撞名** —— 以 SS 的 `carts` 为例：

```
carts_container-cpu-system-seconds-total   ┐
carts_container-cpu-usage-seconds-total    ├ 3 条 → 都会映射到 carts_cpu
carts_container-cpu-user-seconds-total     ┘
carts_container-memory-*  ×7  → 都会映射到 carts_mem
carts_istio-latency-*     ×4  → 都会映射到 carts_latency
```

⇒ 必须「**每个服务每个指标族取一个代表**」，才能得到 `{service}_{指标族}` 节点集。
**这正是 PCMCI 侧采用的抽样方案**，即三方法中唯一能与真值命名对上的那套。

**统一后的成本（反而更低）**：Granger 是成对检验，成本 ∝ n²

| 数据集 | 当前节点 | 统一后约 | 耗时倍率 |
|---|---|---|---|
| RE1-SS | 275 | ~40 | (40/275)² ≈ 1/47 |
| RE1-TT | 761 | ~75 | (75/761)² ≈ 1/100 |

即 TT 的 Granger 从 **3.24 h/例 → 约 2 分钟/例**。变量规模缩小后，重跑成本大幅下降。
