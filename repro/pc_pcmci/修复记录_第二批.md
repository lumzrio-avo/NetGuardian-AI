### `common_features.py` —— 统一变量筛选

原状态是**四套规则**：

| 数据集 | 原规则 | 变量数 |
|---|---|---|
| RE1-OB | 不筛选（只删常量列） | 44~47 |
| RE1-SS | 按 anomaly score 排序 + 去相关 → 上限 40 | 恒 40 |
| RE1-TT | 方差 Top-50 + 去相关（且**豁免真值列**） | 9~31 |
| PCMCI·SS | 方差 Top-50 + 保留全部 latency | 50 |

统一为一套确定性规则（`common_features.select_features`）：

```
1. 删除非特征列（time / time.1）
2. 删除节点级指标（列名第一段以 192- 开头的宿主机指标）
3. 删除常量列（std <= 1e-10）
4. 【强制保留】所有名称含 "_latency" 的列
   —— 通用规则：与案例无关、与真值无关，125 例一视同仁
5. 其余列按【方差降序】取前 (max_features - 已保留数) 列， max_features = 50
6. 去冗余：按方差降序贪心扫描，剔除与已保留列 |corr| > 0.95 的列（第 4 步的列豁免）
```

**在 RE1-TT 真实数据上的实测**（`dataset/RE1-TT.zip` → `ts-auth-service_cpu/1`）：

```
原始 961×1242 → 预处理 961×1154
  删节点级指标 65 个
  删常量列 411 个
  统一筛选后 40 个 = 29 × latency + 11 × memory
```

> ⚠️ **这一节必须写进论文**：官方 `main.py:303` 传 `dk_select_useful=False`，即**使用全部变量**。
> 但实测 PC 在 RE1-SS 的 227~231 个变量上 **990 s/例 + 125 例全部输出全零图**；
> PCMCI 是 PC 的超集只会更严重。**缩规模是被迫的偏离**，本模块只保证"偏离在三系统两方法间一致"。

## 四、路线确认（用户 2026-09-25 决定）

指标级（Mtr）在 SS/TT 上受**三层**限制（详见 `结果/PC与PCMCI_代码审计与统一方案.md` 附录 A）：

| 关 | 含义 | 现状 |
|---|---|---|
| 关一 | 节点在不在图里 | PCMCI·SS/TT 的 cpu / latency 占比 **0%** |
| 关二 | 名字对不对得上 | SS/TT 节点是 Prometheus 长名，官方精确匹配永久失效 |
| 关三 | 排不排得进 top-k | 算法能力 |

**采纳路线 1（复现阶段）**：

- **主指标用服务级（Svc-AC@k）** —— 三方法均可算、可横向比，需注明输入规模不同
- **指标级**：RE1-OB 正常报告；**RE1-SS / RE1-TT 标注 N/A**，理由两条：
  ① 官方命名规则（`main.py:394`）在长名节点上本身就失效（官方既有局限）
  ② 各方法可承受的变量规模差一个数量级（输入不可比）
- 路线 2（"每服务每指标族取代表列" + 节点名改 `{service}_{族}`）留作**阶段三改进**
